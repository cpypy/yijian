### #1 发现页报 UnicodeEncodeError（GBK 编码）

**现象**

点「发现」后整页只有一行错误：

```
加载失败: Traceback (most recent call last): File "runner.py", line 501, in <module>
File "runner.py", line 475, in main File "runner.py", line 468, in discover
UnicodeEncodeError: 'gbk' codec can't encode character '\xf6' in position 103218:
illegal multibyte sequence [PYI-47240:ERROR] Failed to execute script 'runner'
```

**复现**：安装 v0.1.0 → 打开 → 点「发现」。

**期望**：显示全站热榜列表。

**实际**：报错，列表为空。

**根因（已定位，尚未修改）**

sidecar 的 `discover()` 用 `print(json.dumps(...))` 输出 JSON。Windows 上 Python 的
stdout 默认用系统区域编码（cp936/GBK），热榜里有作者名带 `ö` 这类字符（U+00F6），
GBK 编不出来，直接抛 `UnicodeEncodeError`。

本地测试没暴露，是因为当时命令行里设了 `PYTHONIOENCODING=utf-8`；桌面端启动 sidecar
时没有传这个变量。

**候选修法**（等确认后再动）

1. sidecar 启动时 `sys.stdout.reconfigure(encoding="utf-8")`；
2. Rust 启动 sidecar 时补 `PYTHONIOENCODING=utf-8` 环境变量；
3. 两处都做（推荐，双保险）。

**影响面**：不止「发现」——所有通过 stdout 输出的中文/特殊字符事件都可能触发，
只是热榜里恰好有 `ö` 才暴露。

### #2 工作台卡住时没有取消入口

**现象**

输入 `1706.03762` 点「开始」后，界面停在：

```
取源  ▓░░░░░░░░░░░░  0%
等待任务…
```

没有进度、没有日志、没有错误提示，也没有「取消」按钮，只能干等或关掉应用。

**期望**

1. 任务运行时工作台要有**取消**入口（现在代码里其实有这个按钮，但只在 `running=true`
   时显示，说明状态没置上）；
2. 启动失败要能看到具体错误，而不是一直「等待任务…」。

**实际**：按钮仍是「开始」，说明前端认为没有任务在跑；但用户视角就是「点了没反应」。

**待确认**（复现时需要观察）

- 点「开始」后按钮文字有没有变成「加入队列」？
- 应用有没有在后台真的起了 `yijian-engine.exe` 进程？
- 关掉应用重开再点，是否恢复？

**可能原因（未验证，按嫌疑排序）**

1. `start_run` 的 invoke 被拒（Rust 侧 panic/锁），前端 catch 后应写日志，但没看到；
2. 队列 worker 的 `busy` 标志被上一次异常任务卡住，新任务永远排队不执行；
3. sidecar 启动失败（找不到 exe / 缺 DLL），错误事件没冒泡到界面；
4. 前端 `running` 状态与后端实际状态不同步。

**影响面**：这是「主流程不可用」级别——用户没法开始第一篇论文。

**补充证据（第二次复现）**

进度停在 **2%**，日志仍是「等待任务…」，按钮仍是「开始」。

2% 正好是 sidecar 的 `run()` 一进来就发的那条 `{"event":"stage","stage":"fetch","progress":2}`，
说明：

- sidecar **确实启动了**，也成功输出过一条事件；
- 之后就再没有任何事件（没有「任务已创建」、没有错误）；
- 前端 `running` 又是 false（按钮没变），说明 worker 已经退出或从未置位。

**新增嫌疑（第 5 条，已确认是设计缺陷）**

Rust 启动 sidecar 时把 stderr 设成 `Stdio::piped()`，但**从来没有读它**。sidecar 崩溃时
的 traceback 全部堆在这个没人读的管道里，前端只能看到「什么都没发生」。

这解释了为什么「没有错误、没有日志、直接卡住」。

**需要用户提供的信息**

`%LOCALAPPDATA%\Yijian\data\jobs\` 下最新那个文件夹里的 `run.log`，
以及任务管理器里有没有残留的 `yijian-engine.exe`。

**已定位根因（v0.1.0 实测日志）**

```
INFO: startup recovery: {'interrupted': 1, 'needs_auth': 0}
INFO: 127.0.0.1:59344 - "GET /api/tasks HTTP/1.1" 200 OK
INFO: 127.0.0.1:59344 - "POST /api/arxiv/1706.03762/translate HTTP/1.1" 409 Conflict
```

texlate server 启动时恢复出 **1 个 interrupted 任务**（上一次卡死的残留），
再提交同一篇论文时被判为重复，返回 **409 Conflict**。

sidecar 把 409 当失败直接返回，前端只看到「卡在 2%」。

**因此是三层问题叠加**

1. 上一次任务异常退出留下 `interrupted` 残留，服务端不会自动清理；
2. sidecar 把 409 当错误，而不是「复用已有任务」；
3. 即使返回错误，界面也没显示出来（错误事件丢失 / 用户没看到日志区）。

**修复方向**

- 409 时从响应里取 `task_id`，直接轮询那个任务（复用），而不是报错；
- 或在提交前先 `DELETE /api/task/{id}` 清掉同名残留，再重试一次；
- 启动时若 recovery 出 interrupted 任务，UI 上给出「上次中断」提示并提供清理。

### #5 模型端点 502，任务无限重试且不报错（#3 的真正原因）

**现象（v0.1.1 实测日志）**

```
INFO: POST /api/arxiv/1706.03762/translate 202 Accepted
INFO: head 1706.03762
WARNING model swe-2-medium 失败（HTTP 502: ）→ 枚举免费集降级候选
WARNING 免费集发现失败（HTTP 502: ）——模型降级臂停用
WARNING autogloss: 第 1/6 批放弃（HTTP 502: ）
...
WARNING autogloss: 6 批 → 0 词
（之后每 4 秒重复一次 502）
```

**诊断**

1. 模型名是 `swe-2-medium`，这不是应用里配置的模型名，说明 texlate 用的是**内置默认值**
   —— 我们只把非空的 `base_url`/`model`/`api_key` 传下去，用户很可能只填了 Key，
   Base URL 和模型留空，于是 texlate 走了它自己的默认网关。
2. 那个默认网关返回 **502**，texlate 的降级链路（免费集）也 502，于是每次都失败。
3. texlate 对模型失败是**无限重试**，任务状态停在 `translating`，进度自然不动。

**这解释了 #3**：不是续跑逻辑坏了，是模型调不通，进度卡在原地。

**问题清单**

- 配置不完整（只填 Key）时没有校验，直接用了默认端点；
- 端点不通时没有「快速失败 + 明确提示」，只有无限重试；
- 界面看不到「模型 502」这种关键信息（只在 run.log 里）。

**修复方向**

1. 设置页把 Base URL / 模型 / Key 三项都设为必填，缺一项就提示；
2. 保存时做一次**连通性测试**（发一条最小请求），失败直接提示；
3. sidecar 检测到连续 N 次 502/401，直接失败并提示「模型不可用，请检查配置」，
   而不是让用户干等；
4. 日志区把 `[stderr]` 和引擎的 WARNING 都显示出来。

**严重度**：阻断（配置对了才能用）

- 遇到 `duplicate_active`：如果用户选了「继续」，就附着到那个 task 轮询；

### #8 v0.1.2 卡在 2%，冲突弹窗不出现

**现象（v0.1.2 实测）**

输入 `1706.03762` → 开始 → 停在「取源 2%」，日志只有「等待任务…」，没有弹窗，没有报错。

**这是卡住了吗**：是。而且是我这版引入的 bug。

**根因（已定位）**

sidecar 检测到旧任务时输出的是**一行嵌套事件**：

```json
{"event": "conflict", "task_id": "...", "status": "interrupted", "progress": 3}
```

Rust 把所有 sidecar 输出统一包成 Tauri 的 `engine-event` 发出去，payload 才是上面这个对象。

但前端我写成了**单独监听 `"conflict"` 事件**：

```ts
listen("conflict", ...)   // 永远收不到
```

正确写法应该是在 `engine-event` 的回调里判断 `p.event === "conflict"`。

**后果链**

1. 弹窗不出现；
2. sidecar 发完 conflict 就正常退出（return 0）；
3. worker 广播 `engine-exit`，前端 `running=false`；
4. 界面停在 2%，日志空白，用户只能干等。

**修复方向**

```ts
if (p.event === "conflict") {
  running = false;
  conflict = p;
  return;
}
```

放在现有的 `engine-event` 处理函数里，删掉那个独立监听。

**顺带**：这类「事件名对不上」的问题应该加个兜底——未知 `event` 类型时在日志里打出来，
而不是静默丢弃。

**严重度**：阻断（v0.1.2 上等于又回到 #2）

### #12 发现页点「译成中文」之后很卡

**实测**：约 **9 秒**才出结果。

**原因（基本确定）**

1. 每次点击都 spawn 一个新的 `yijian-engine.exe`，PyInstaller 启动 + 导入 texlate 要 2–5 秒；
2. 标题和摘要**分两次**请求，一次往返十几秒，串行叠加；
3. 没有缓存，同一张卡片点两次就调两次模型。

**期望**：点下去 3 秒内有结果，第二次点立即出（命中缓存）。

**修法**

- 标题 + 摘要合成**一次**请求（用分隔符），往返减半；
- 结果按 arxiv ID 缓存（内存 + 磁盘），重复点击直接读；
- 引擎常驻或复用会话，避开冷启动。

**严重度**：中（能用，体感差）

### #13 PDF 只显示前 3 页，往下滚不出新页

**现象**：阅读器里 PDF 只有 3 页，滚到底也不继续加载。

**根因（已定位，未修改）**

`PdfViewer.svelte` 用 IntersectionObserver 监听的是**滚动容器自己**（`root: host`，`observe(host)`）。
容器始终和自己相交，回调只触发一次，于是只渲染了首批 3 页，之后再没有任何触发点。

**修法**：在页面列表末尾放一个哨兵元素（sentinel），观察它；每次进入视口就 `renderNext(3)`。
或者改用滚动事件：`host.scrollTop + host.clientHeight > host.scrollHeight - 800` 时加载。

**严重度**：高（长论文根本读不完）

### #14 对照模式完全没有高亮效果

**现象**：切到「对照」，两边 PDF 都能看，但鼠标移上去没有任何高亮，也不会联动滚动。

**修法**

- 先修 #13，让整篇渲染出来；
- 给旧论文加「重建对齐」：读已有 PDF + segments 重新算 align，不用重译；
- 对齐失败的段落给出明确提示（而不是静默无高亮）。

**严重度**：中（功能宣称有，实际不可用）

实际应用只做了左侧导航和输入卡片，其余没落地。

**差距清单**

| 概念稿 | 应用现状 |
|---|---|
| 工作台：队列列表（进度条、上下移、移除） | 只有一行「队列 N」，点开才有简易列表 |
| 工作台：最近阅读 | 没有 |
| 文库：表格（标题/标签/进度/状态） | 还是行式卡片 + 下拉 |
| 阅读器：左侧目录 + 右侧笔记 | 只有 PDF 双栏 |
| 顶栏：今日用量、打开数据目录 | 只有标题和 tokens |

**严重度**：中（观感落差，非功能阻断）
