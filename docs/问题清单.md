## 问题列表

### #1 发现页报 UnicodeEncodeError（GBK 编码）

**现象**

点「发现」后整页只有一行错误：

```
加载失败: Traceback (most recent call last): File "runner.py", line 501, in <module>
File "runner.py", line 475, in main File "runner.py", line 468, in discover
UnicodeEncodeError: 'gbk' codec can't encode character '\xf6' in position 103218:
illegal multibyte sequence [PYI-47240:ERROR] Failed to execute script 'runner'
```

**复现**：安装 v0.1.0 → 打开 → 点「发现」。

**期望**：显示全站热榜列表。

**实际**：报错，列表为空。

**根因（已定位，尚未修改）**

sidecar 的 `discover()` 用 `print(json.dumps(...))` 输出 JSON。Windows 上 Python 的
stdout 默认用系统区域编码（cp936/GBK），热榜里有作者名带 `ö` 这类字符（U+00F6），
GBK 编不出来，直接抛 `UnicodeEncodeError`。

本地测试没暴露，是因为当时命令行里设了 `PYTHONIOENCODING=utf-8`；桌面端启动 sidecar
时没有传这个变量。

**候选修法**（等确认后再动）

1. sidecar 启动时 `sys.stdout.reconfigure(encoding="utf-8")`；
2. Rust 启动 sidecar 时补 `PYTHONIOENCODING=utf-8` 环境变量；
3. 两处都做（推荐，双保险）。

**影响面**：不止「发现」——所有通过 stdout 输出的中文/特殊字符事件都可能触发，
只是热榜里恰好有 `ö` 才暴露。

### #2 工作台卡住时没有取消入口

**现象**

输入 `1706.03762` 点「开始」后，界面停在：

```
取源  ▓░░░░░░░░░░░░  0%
等待任务…
```

没有进度、没有日志、没有错误提示，也没有「取消」按钮，只能干等或关掉应用。

**期望**

1. 任务运行时工作台要有**取消**入口（现在代码里其实有这个按钮，但只在 `running=true`
   时显示，说明状态没置上）；
2. 启动失败要能看到具体错误，而不是一直「等待任务…」。

**实际**：按钮仍是「开始」，说明前端认为没有任务在跑；但用户视角就是「点了没反应」。

**待确认**（复现时需要观察）

- 点「开始」后按钮文字有没有变成「加入队列」？
- 应用有没有在后台真的起了 `yijian-engine.exe` 进程？
- 关掉应用重开再点，是否恢复？

**可能原因（未验证，按嫌疑排序）**

1. `start_run` 的 invoke 被拒（Rust 侧 panic/锁），前端 catch 后应写日志，但没看到；
2. 队列 worker 的 `busy` 标志被上一次异常任务卡住，新任务永远排队不执行；
3. sidecar 启动失败（找不到 exe / 缺 DLL），错误事件没冒泡到界面；
4. 前端 `running` 状态与后端实际状态不同步。

**影响面**：这是「主流程不可用」级别——用户没法开始第一篇论文。

**补充证据（第二次复现）**

进度停在 **2%**，日志仍是「等待任务…」，按钮仍是「开始」。

2% 正好是 sidecar 的 `run()` 一进来就发的那条 `{"event":"stage","stage":"fetch","progress":2}`，
说明：

- sidecar **确实启动了**，也成功输出过一条事件；
- 之后就再没有任何事件（没有「任务已创建」、没有错误）；
- 前端 `running` 又是 false（按钮没变），说明 worker 已经退出或从未置位。

**新增嫌疑（第 5 条，已确认是设计缺陷）**

Rust 启动 sidecar 时把 stderr 设成 `Stdio::piped()`，但**从来没有读它**。sidecar 崩溃时
的 traceback 全部堆在这个没人读的管道里，前端只能看到「什么都没发生」。

这解释了为什么「没有错误、没有日志、直接卡住」。

**需要用户提供的信息**

`%LOCALAPPDATA%\Yijian\data\jobs\` 下最新那个文件夹里的 `run.log`，
以及任务管理器里有没有残留的 `yijian-engine.exe`。

**已定位根因（v0.1.0 实测日志）**

```
INFO: startup recovery: {'interrupted': 1, 'needs_auth': 0}
INFO: 127.0.0.1:59344 - "GET /api/tasks HTTP/1.1" 200 OK
INFO: 127.0.0.1:59344 - "POST /api/arxiv/1706.03762/translate HTTP/1.1" 409 Conflict
```

texlate server 启动时恢复出 **1 个 interrupted 任务**（上一次卡死的残留），
再提交同一篇论文时被判为重复，返回 **409 Conflict**。

sidecar 把 409 当失败直接返回，前端只看到「卡在 2%」。

**因此是三层问题叠加**

1. 上一次任务异常退出留下 `interrupted` 残留，服务端不会自动清理；
2. sidecar 把 409 当错误，而不是「复用已有任务」；
3. 即使返回错误，界面也没显示出来（错误事件丢失 / 用户没看到日志区）。

**修复方向**

- 409 时从响应里取 `task_id`，直接轮询那个任务（复用），而不是报错；
- 或在提交前先 `DELETE /api/task/{id}` 清掉同名残留，再重试一次；
- 启动时若 recovery 出 interrupted 任务，UI 上给出「上次中断」提示并提供清理。
